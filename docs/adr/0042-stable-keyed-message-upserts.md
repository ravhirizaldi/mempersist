# ADR 0042: Stable keyed message upserts

- Status: Accepted
- Date: 2026-10-05

## Context

Canonical conversations are immutable revision documents in R2. A conversation can contain an
active branch and inactive alternate branches, while FTS, chunks, and Vectorize remain derived,
lagging, and rebuildable. Source-node IDs are useful when a caller has read the graph, but RP and
structured-state clients also need an application-owned identity that survives text edits and can be
used without resubmitting an entire transcript.

Issue #13 added exact revision-pinned reads through `memory_get_messages`, including optional
`message_key` selectors. Issue #7 completes that contract with a write path. The key must identify
one node in the complete canonical graph, not merely the current active projection, and the write
must retain the existing R2-before-D1 compare-and-swap durability boundary.

## Decision

### 1. Key schema and graph invariant

`CanonicalNode.messageKey?: string` is optional. When present, it is exactly 1–128 lowercase
ASCII characters from `[a-z0-9._/-]`, begins and ends with an alphanumeric character, and is
case-sensitive. Keys are unique across the complete graph of one canonical revision, including
inactive branches. A malformed or duplicate key is a canonical-storage/integrity error; lookup and
upsert never choose an arbitrary duplicate.

A key is immutable node identity. It is not normalized, trimmed, case-folded, or regenerated by an
update. A copied conversation has a distinct graph and may contain the same application keys as its
source, but a destination graph must still satisfy the complete-graph uniqueness invariant.

### 2. Bounded upsert request

`memory_upsert_messages` accepts 1–100 unique keyed text messages for one owned, non-deleted
conversation. Every request supplies an explicit `base_revision_id`, `message_key`, text, and role.
The server validates ownership, conversation/revision membership, batch size, key syntax, duplicate
request keys, text limits, and role values before any canonical write. Missing, foreign, deleted,
and unowned conversations have the same bounded non-revealing outcome.

For an existing key, the operation replaces text only. It preserves source-node ID, role,
`createdAt`, parent/child graph links, active/inactive branch membership, raw fields, and metadata;
`updatedAt` changes only when text changes. A role mismatch rejects the whole request. For a missing
key, the server creates a server-ID/server-timestamp keyed canonical text node after the active
current node, preserving request order. The result is one complete canonical graph, so a key that is
present only on an inactive branch is an update rather than a new append.

### 3. Atomic canonical commit

All request validation and materialization completes before writing. A changed request produces one
new immutable revision regardless of the number of changed or appended items. The server writes the
canonical manifest and segment to R2 first, then advances the conversation head with a D1 CAS
against `base_revision_id`. A stale base fails without overwriting the current head; a failed
validation or CAS creates no current revision and no eligible index job.

When every supplied text already equals its keyed node, the result is `status: "no_change"` against
the current revision. It writes no R2 revision, D1 head transition, queue job, FTS row, or vector.
Indexing is enqueued only after a successful head transition. Queue failure is post-commit and does
not roll back canonical state. Optional verification reloads the committed revision through the
canonical integrity path and checks every requested key, role, exact text, and revision hash.
Durability, indexing, and verification remain separate receipt states.

### 4. Relationship to other mutations

Upsert is not an alias for another write surface:

- `memory_append` adds new unkeyed message nodes.
- `memory_edit_messages` targets known immutable `source_node_id` values and can replace, append,
  or prepend text, without changing key identity or graph metadata.
- `memory_replace` supplies a complete intended transcript and is responsible for complete-transcript
  materialization.
- `memory_upsert_messages` addresses keyed field-level state and never silently rebases a stale
  request or changes key identity, role, graph, or metadata.

### 5. Copies, restore, export, and integrity

Lossless conversation copy reads a pinned complete revision and preserves `messageKey` on active and
inactive nodes while assigning destination node IDs and a new conversation/revision identity. The
source remains immutable. Revision restore reactivates the exact historical key set and does not
rewrite keys. Full account exports include `messageKey`; import and restore paths validate key shape
and complete-graph uniqueness before accepting canonical content.

Integrity verification checks key syntax and duplicate-free complete graphs in addition to manifest and
segment hashes. If canonical objects are missing or corrupt, operators restore them from an
independent canonical export and rerun integrity checks. FTS, Vectorize, chunks, search snapshots,
and offsets are never used to reconstruct keyed message identity or exact text.

## Compatibility

Existing nodes without `messageKey` remain valid and continue to use source-node lookup. Existing
source-node reads, append/edit/replace semantics, immutable historical revisions, copy provenance,
restore transitions, and canonical R2 object formats remain unchanged. `memory_get_messages` accepts
both `source_node_id` and `message_key`; key reads are canonical-only and revision-pinned, including
inactive branches. The capabilities response advertises `features.message_keys: true` when this
write/read contract is deployed. No FTS, Vectorize, or D1 key index is required.

## Alternatives considered

### Put keys in a derived D1 or search index

Rejected. Derived state can lag, be deleted, or represent only an active projection. Exact identity
must remain available from the complete canonical revision and must not depend on FTS or Vectorize.

### Make keys globally unique across conversations

Rejected. Application fields such as `state.relationship` are naturally scoped to an owner
conversation. Global uniqueness would add an unnecessary cross-conversation coordination constraint;
complete-graph uniqueness is sufficient and compatible with lossless copies.

### Mutate a node in place

Rejected. In-place mutation would make historical reads and restore ambiguous. Every changed upsert
creates one immutable revision while preserving the canonical revision history.

### Rebase a stale request onto the latest head

Rejected. Automatic rebasing could update a different graph or branch than the caller read. The
explicit base revision and CAS provide predictable optimistic concurrency; callers reread and retry
with new intent after a conflict.

### Resubmit a complete transcript for keyed state

Rejected. It is lossy for inactive branches and raw metadata and creates avoidable race and payload
risk. Upsert changes only the requested keyed text or appends the missing keyed nodes.

### Treat a no-op as a new revision

Rejected. A no-op would create unnecessary canonical objects, head transitions, and index work. The
explicit `no_change` result preserves revision stability and makes retries cheap.

## Consequences

- RP and structured-state clients have a stable application identity for exact text updates.
- Key validation and uniqueness apply to the complete graph, so inactive branches cannot hide a
  collision.
- Canonical durability remains authoritative even when queueing, verification, or response shaping
  fails; operators repair derived state after the commit.
- Copies, restore, and exports retain keyed identity without adding a second key-resolution store.
- Clients must retain and supply a base revision and must treat stale conflicts as reread/recompute
  boundaries.

## Non-goals

- Fuzzy, text-based, title-based, offset-based, FTS-based, or Vectorize-based key resolution.
- Keys on every canonical node, global key uniqueness, key renaming, deletion, or mutable role/graph
  metadata through this tool.
- In-place mutation, automatic stale-request rebasing, partial commits, or cross-conversation atomic
  upserts.
- A new R2 prefix, D1 key index, search-index schema, or distributed transaction across R2, D1,
  Queues, Workers AI, and Vectorize.
- Reconstructing canonical text from derived indexes or exposing internal R2 keys, D1 row IDs, or
  tenant ownership details.
